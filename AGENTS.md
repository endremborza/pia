# Agent guide

Settled decisions for iterating on this repo. Don't relitigate them mid-task; if one changes, update this file.

## What this is

Paper improvement agent: upload a paper, get a peer review grounded in Semantic Scholar/OpenAlex, edit by natural-language command, export — citations always intact. README.md is the design map; docs/ holds the system-design writeups.

This repo *is* the `papercli` library: a publishable, installable Python package (`papercli` on PyPI, import `papercli`), whose two adapters are the `papercli` console script and the FastAPI server. The SvelteKit frontend lives in the same repo but is not part of the distribution.

## Settled architecture

- Vocabulary: the unit of work is a **papercli repo** — the paper as git-versioned LaTeX source in this app's standard layout. Use that term in code, docs and UI; never "LaTeX project", "LaTeX source directory" or "paper project". Rationale (README): an LLM on a PDF is an LLM on an image — six fingers; an LLM on source is text completion. Conversion therefore happens first, not last.
- The thesis the project demonstrates: an LLM agent is most reliable in a **sandbox with familiar tools and hard output contracts**. The papercli repo is that sandbox — one root, fixed layout, git as the state model, the toolbox coding agents are already fluent in. Where correctness matters, it is never left to prompting: references are CSL-JSON verified by hallubib, reviews are RelaxNG-validated XML, edits are git diffs checked against a path allowlist and the cite-key validator. The agent is free where free-form is its strength (writing LaTeX) and structurally constrained everywhere a contract must hold. The end state is a sandbox repo plus a set of skills any agent can call.
- `main.tex` is the canonical representation inside the repo. Structure view, citation list, parity report are derived and read-only — never make a derived view mutable, never edit anything but the LaTeX.
- CLI-first: the core is a library; `papercli` (console script of this package) and the FastAPI server are two thin adapters over the same functions — the server imports the core, never shells out to the CLI. The frontend mirrors CLI verbs and stays a first-class surface, not an afterthought.
- Library boundary, enforced structurally: the server lives in `papercli.server` behind the `[server]` extra (fastapi/uvicorn/python-multipart are not core deps) and `papercli serve` imports uvicorn lazily; core never imports `papercli.server`; nothing in the package knows the frontend exists. The module that executes a repo's `[build]` code must stay unimportable from `papercli.server` — that is the security boundary in structural form, worth one import test.
- Publishable means no repo-relative paths inside the package: the RelaxNG schema, default `.csl` styles and any bundled templates load through `importlib.resources.files("papercli")`, never by walking up from `__file__`. The projects root for web uploads comes from config with a platform default (`~/.local/share/papercli/projects`) — never a path relative to the package or the CWD.
- `papercli/__init__.py` is the public API surface: curated re-exports, `py.typed` shipped, version single-sourced from `__version__` via hatchling. Dependencies are plain PyPI releases (`hallubib>=0.3.0`, `paritex>=0.1.0`) — no `[tool.uv.sources]`, no path links — so the wheel installs anywhere; a change needed in a dep is released there first, then the pin here moves forward.
- Config is layered: built-in defaults < `~/.config/papercli/config.toml` < the repo's `pyproject.toml` `[tool.papercli]` (optional) < flags. There is no `papercli.toml`: papercli never writes a config file into a repo and never searches upward for one — the only repo-level config is a `pyproject.toml` at the papercli repo's git root. Repos papercli creates (PDF or `.tex` ingest) contain no Python and therefore no repo-level config; they run entirely on the user layer. A repo adopted by `papercli init` from a real paper project already has a `pyproject.toml`, because the code generating its figures and tables has dependencies — that is exactly where `[tool.papercli.build]` belongs. Key names are identical under both roots; the `tool.papercli` prefix is stripped on read so one config dataclass parses both. No secrets in a repo's pyproject — API keys come from env or user config.
- CSL-JSON is the only reference model, keyed by cite key (`refs.json` in the project). Every `.bib` is derived — regenerated from the store via hallubib for builds, never hand-maintained. Bibliography rendering goes through citeproc + `.csl` styles — never string templates or regex formatting.
- Citation integrity is enforced by a validator diffing the cite-key multiset and reference store before/after every edit. Every path an agent writes through is gated before commit: edit runs against a path allowlist plus the multiset check, review runs scoped to their own `reviews/N/` directory so a review cannot touch the paper or the store at all. Review documents' `<cite>` elements are checked against the store the same way, and new references only ever enter the store through the harness, from the run's fetch log.
- Source honesty: any paper id, DOI or title shown to the user must come verbatim from an OpenAlex / Semantic Scholar / Crossref / arXiv API response. Never synthesize one. Failures — unresolved references, empty searches, low-confidence matches, parity gaps — are surfaced in the UI, not swallowed.
- Review findings are canonical as `reviews/N/review.xml` (N matches the `review/N` tag), validated against a RelaxNG schema shipped as `papercli` package data (lxml). The schema requires every finding to carry a `<source>` element with a verbatim API id — ungrounded findings are unrepresentable. `review.tex` and its bibliography are generated from the XML in Python (no XSLT); the API serves derived JSON to the frontend; XML stays canonical on disk.
- hallubib (my lib, on PyPI, developed at `../../apps/hallubib`) does reference resolution and the confidence taxonomy. Missing capabilities get thin adapters here — don't fork or vendor it; extending it means a hallubib release plus a pin bump here.
- paritex (my lib, on PyPI, developed at `../../apps/paritex`) owns PDF → papercli-repo reconstruction and parity checking, and with them the produced-files contract: the fixed file names (`main.tex`, `refs.bib`, `assets/`, `report.json`, `original.pdf`) are paritex constants imported from there, never restated here. Same rule as hallubib: extend it there — via a release, not a path link — not here.
- A reconstruction is a *guess* (a paper's source is not recoverable from its rendering) and gets two verdicts: paritex's parity score plus structural gates (machine) and an explicit **user acceptance step** (human). Acceptance is a first-class pipeline stage, not UI polish: the frontend shows the rebuilt PDF against the original with divergences and extracted citations — "this is your paper rendered from our idea of what it is" — and offers accept (tags `parse/N`, unlocks review/edit), refine (another reconstruction-backend pass over this candidate, steered by a user instruction plus the parity feedback; paritex's `refine()`), or re-run (a fresh reconstruction from the committed `original.pdf`, never a re-upload). Reconstruction defaults to one automatic round (`[reconstruct] rounds = 1`); further passes are the user's call via refine. No downstream stage runs on an unaccepted reconstruction, and a bad reconstruction is refined or re-run through the reconstruction backend, never hand-patched by the edit agent. Rationale: PDF parsing is the one expensive, error-prone step, so it is concentrated at ingest, paid for once per paper, and gated once — turning a recurring accuracy problem into a single reviewed decision.
- A papercli repo is any directory with the standard layout — paritex's produced files plus this app's overlay (`refs.json`, `reviews/`) — and its own git repo, the only durable state; no database. Web uploads create repos under the gitignored projects root; `papercli init` adopts an existing directory in place. The UI reads committed refs only, never the working tree; live run progress streams separately and is never persisted.
- Web ingest is a single `.tex` file or a PDF — never an archive or a directory. Multi-file repos (assets, figure/table generation code) come only from `papercli init` on a local directory the user already trusts.
- The server executes no code from a repo but tectonic. Figure/table generation (`[tool.papercli.build]`) runs under the CLI only. This is a security boundary, not a convenience split — do not add a "run the project's build" path to the API. It is also self-reinforcing: web ingest cannot produce a `pyproject.toml`, so a server-created repo has no `[build]` table to run in the first place. Public exposure is gated by `PAPERCLI_PASSWORD` (env): when set, every request but `/api/health` requires HTTP Basic with that password — the only auth layer in the system; a public deployment must set it.
- Deterministic steps (parse, hallubib resolution, parity, citeproc, tectonic) are plain functions the server runs and commits. The agent handles judgment only — claim extraction, support verdicts, edits, reconstruction refinement. Skills the agent calls are thin wrappers over those same functions: one implementation, two callers (CLI verb and skill).
- Agent runs execute *inside* the sandbox: `claude -p` with cwd = the papercli repo, on a proposal branch, with skills and permission settings materialized into the repo's `.claude/` from package data before every run (the toolbox is papercli-versioned, so `.claude/` is listed in the repo's gitignore and regenerated, never committed). The agent edits `main.tex` directly — no typed-operation planner; that design is superseded. Safety comes from gates, not restraint: after the run, code checks the diff against a path allowlist, recompiles with tectonic, and runs the citation validator — a violating run is rejected wholesale, never partially applied.
- Source honesty is mechanical, not prompted: the search skill (`papercli search`) records every API record it returns verbatim into the run's `sources.json`; review validation requires every `<source>` id to appear in that fetch log or the existing store. An id the agent made up fails schema-or-log validation and the run is rejected.
- Agent runs happen on proposal branches; approve = server-side fast-forward merge, reject = branch delete. The agent never commits (the harness commits gate-passing results), never force-pushes, never rewrites history. The cite-key validator gates every commit.
- One run per repo: a lock file in the repo (CLI and server are separate processes); a busy repo surfaces "someone is currently working on this" in the UI. Everything that moves HEAD holds it, approve and reject included — a disabled button in the UI is not enforcement.
- Milestones are tags (`parse/N`, `review/N`, `export/N`). Never commit regenerable artifacts: no rendered PDFs; the original PDF only when PDF was the upload (source uploads commit no PDF).
- All LLM work goes through the agent runner module: headless `claude -p` today, Claude Agent SDK as the planned drop-in. The runner is selected and parameterized by the config's `[agent]` table, which reuses paritex's backend-spec schema — one AI-invocation config shape in the system, including its env controls (`env`/`drop_env`/`require_env`). Auth is explicit in the backend, never inherited: `claude-code` (default) scrubs the Anthropic auth env vars and runs on the box's Claude Code login; `claude-api` requires `ANTHROPIC_API_KEY` and bills the API deliberately. Both come from paritex's `claude_backend()` factory (papercli extends `--allowedTools` and maps the config's `model`/`effort` keys to `--model`/`--effort` — `[agent]` defaults to the box's Claude Code settings, `[reconstruct]` to sonnet/medium, both user-overridable per run in the UI and CLI; custom backends own their argv and ignore these keys); selection is config `[agent] backend` or the `PAPERCLI_AGENT_BACKEND` env var. Nothing outside that module may depend on which one runs. Each run type (review, edit) has one small prompt naming the contract to satisfy; capability comes from the skills in the sandbox, not from prompt bulk — no giant do-everything prompt.
- git subprocess calls live in exactly one module (the git store); no git via subprocess anywhere else. Other external binaries (tectonic, claude) get one wrapper module each.
- `.git/` is the one path a diff gate cannot cover, because git never reports its own directory as dirty — and several config keys (`core.fsmonitor`, `core.hooksPath`, `diff.external`, `diff.*.textconv`, `filter.*.clean`) name commands git runs on the harness's behalf, so a repo-local config is an execution primitive. Two defences, both structural: the git store states the dangerous settings on every command line, where they beat any config file, and every agent run is wrapped in `agentrun.sealed`, which restores `.git/config` and rejects the run if it changed. Neither belongs at a call site; do not add a git invocation that bypasses the store.
- Stack: Python 3.13, uv-managed, hatchling-built — `papercli` CLI + FastAPI server over one core, lxml for review-schema validation; SvelteKit + Svelte 5 + TypeScript frontend; tectonic for LaTeX builds.

## Code standards

- Python: type hints everywhere, pyright-clean; ruff formats; dataclasses for structured data; functional, minimal-mutation style in data-heavy paths.
- Always uv, never pip: `uv add`, `uv run`. The dev environment needs the extra: `uv sync --extra server`, `uv run --extra server ...` for anything touching the API.
- Fail loudly and early; clear error types; no defensive over-engineering.
- Minimal comments — code self-documents. No tutorial-style commentary.
- DRY, small focused functions. If a new feature supersedes an old one, delete the old one.
- Svelte: logic in TS utils, no business logic in markup, small components, semantic HTML, minimal CSS.
- Tests: minimal but real, on core behavior — reference segmentation, cite-key validator, resolver adapters, operation application. No heavy integration scaffolding.

## Workflow

- The human does all committing.
- Markdown: one line per paragraph and per list item, never hard-wrap prose.
- docs/ is committed, as-built, for anyone reading the code. .cril/ is private planning (gitignored) — never link to it from docs/ or code. When a planned piece ships, fold its as-built description into docs/ and remove it from the plan.
